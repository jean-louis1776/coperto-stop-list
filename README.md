# Стоп-лист кухни

Панель, в которой менеджер зала видит меню смены, фильтрует его по цеху и статусу и ставит позиции в стоп-лист или возвращает их в продажу.

**Превью:** [Жми сюда](https://coperto-stop-list.vercel.app/)

## Запуск

Нужны Node.js 20.9+ (я работал на 24) и pnpm. Если pnpm не установлен, его можно включить через Corepack: `corepack enable`.

```bash
pnpm install
pnpm dev
```

Приложение откроется на http://localhost:3000.

Остальные команды:

| Команда             | Что делает                          |
| ------------------- | ----------------------------------- |
| `pnpm build`        | production-сборка                   |
| `pnpm lint`         | ESLint                              |
| `pnpm format:check` | проверка форматирования Prettier    |
| `pnpm typecheck`    | генерация типов роутов Next и `tsc` |
| `pnpm test`         | юнит-тесты (Vitest)                 |

Все эти проверки гоняются в GitHub Actions на каждый пуш и PR.

## Стек

Next.js 16 (App Router), React 19, TypeScript в strict-режиме, Tailwind CSS 4, TanStack Query 5, Zustand, React Hook Form + Zod, Motion (бывший Framer Motion), Vitest + Testing Library.

## Как устроен проект

```
app/
  page.tsx                     серверный компонент: читает searchParams, делает prefetch
  layout.tsx, providers.tsx    шрифт, QueryClient, тосты
  api/menu-items/...           мок-API на route handler'ах
entities/menu/                 доменные Zod-схемы, типы, подписи
features/stop-list/
  api/                         запросы к API — только транспорт
  model/                       ключи кэша, мутации с оптимистикой, фильтры в URL, UI-стор
  ui/                          компоненты фичи
shared/
  api/                         fetch-обёртка и контракт ошибки
  lib/                         мелкие утилиты
  model/                       стор тостов
  ui/                          Button, Select, Field, Badge, Spinner, Toaster, CloseButton
server/                        in-memory хранилище, имитация задержек и ошибок
```

Слои разложены примерно как в Feature-Sliced Design: `shared` ничего не знает о домене, `entities` — о фичах, а UI-компоненты не знают о транспорте. Компоненты получают данные и колбэки через пропсы или хуки из `model`, а сами запросы лежат в `features/stop-list/api`.

От структуры из задания отошёл в одном месте: доменные типы лежат не в `types/menu.ts`, а в `entities/menu` рядом со схемами, из которых они выводятся.

### Где проходит граница между сервером и клиентом

- `app/page.tsx` — серверный компонент. Он читает `searchParams`, прогоняет их через ту же схему фильтров, что и API, берёт данные напрямую из хранилища (без HTTP-запроса к самому себе) и передаёт их клиенту через `HydrationBoundary`. Поэтому первый экран приходит уже с данными, без лоадера и скачка вёрстки.
- `features/stop-list/ui/StopListScreen.tsx` — точка входа в клиентскую часть (`'use client'`). Всё интерактивное находится ниже неё: фильтры, таблица, панель, формы.
- Фильтры меняются через `history.pushState`, а не через `router.push`. Next синхронизирует такие изменения с `useSearchParams`, поэтому смена фильтра не гоняет лишний запрос к серверу за RSC, а данные подгружает TanStack Query. Кнопка «назад» и перезагрузка страницы работают как обычно.
- Модули в `server/` помечены `server-only` и не попадут в клиентский бандл даже по ошибке.

## Решения и почему

Схемы Zod — единственный источник правды: из них выводятся типы, и одна и та же схема проверяет форму на клиенте и тело запроса в route handler. Оптимистичное обновление применяется ко всем закэшированным спискам, а при ошибке откатывается только изменённая позиция, а не весь список целиком, — так параллельные мутации не затирают друг друга. Перезапрос списка после мутации запускается, только когда завершилась последняя активная мутация, иначе строки мигали бы. В Zustand лежит только UI-состояние (какая позиция открыта в панели и очередь тостов), а серверные данные живут в кэше TanStack Query.

Ещё несколько деталей:

- Тост об ошибке показывается глобально через `MutationCache`, поэтому хуки мутаций про уведомления не знают, и следующая фича получит тосты без лишнего кода.
- У таблицы фиксированные ширины колонок. Иначе при смене бейджа статуса колонки пересчитывались бы и кнопки в строках прыгали.
- Время в бейдже рендерится только на клиенте: на Vercel сервер работает в UTC, и серверный рендер показал бы не то время, что у пользователя.
- Ручная мемоизация (`memo`, `useCallback`, `useMemo`) стоит там, где она реально экономит рендеры: строки таблицы, таблица, фильтры. React Compiler специально не включал.

### Чем отличается от примера `useStopItem` из задания

В задании пример хука помечен как ориентир, а не эталон, и отступления от него разрешены, если объяснить причину. Основу я оставил той же: оптимистичное изменение в `onMutate`, `cancelQueries`, откат в `onError`, инвалидация в `onSettled`. Но в нескольких местах сделал иначе, потому что пример ломается в обычных сценариях:

| В примере                                                    | У меня                                                                                 | Что было бы не так                                                                                                              |
| ------------------------------------------------------------ | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Хук принимает `filtersKey` и обновляет только текущий список | Хук без аргументов, обновляет все закэшированные списки через `setQueriesData`         | Поставил позицию в стоп на «Все цеха», переключился на «Кухню» — там из кэша она ещё «в продаже», пока список не перезапросится |
| При ошибке весь список заменяется снимком `prev`             | Запоминается и откатывается только изменённая позиция                                  | Поставил в стоп A, сразу B. A упала — откат к снимку затирает оптимистичное изменение B. Этот сценарий покрыт тестом            |
| `invalidateQueries` в `onSettled` вызывается всегда          | Перезапрос только когда завершилась последняя активная мутация                         | A завершилась, список перезапрашивается, пока B ещё в пути. Сервер про B ещё не знает, и строка B мигает обратно                |
| Хук только для постановки в стоп                             | Общая логика в `useOptimisticItemMutation`, поверх неё `useStopItem` и `useResumeItem` | Для возврата в продажу пришлось бы копировать тот же хук                                                                        |

Сверх примера мутация ещё подставляет в кэш позицию из ответа сервера (`onSuccess`), а по `mutationKey` строка понимает, что она сейчас сохраняется.

## Допущения

Кое-что в задании можно было трактовать по-разному. Вот как я решил:

- **Редактирование стопа.** Отдельного эндпоинта в задании нет, поэтому повторный `POST /api/menu-items/:id/stop` для позиции, которая уже в стопе, просто обновляет причину и срок.
- **Панель и оптимистика.** Статус в строке меняется сразу после отправки формы, а панель ждёт ответа сервера и показывает лоадер на кнопке. Если сервер вернул ошибку, строка откатывается, появляется тост, а форма остаётся открытой — можно сразу отправить ещё раз.
- **Ошибка загрузки списка.** Кроме ~20% ошибок на мутациях, `GET` тоже падает примерно в 10% случаев — иначе состояние ошибки списка просто не увидеть.
- **Остаток.** Менять его в интерфейсе нельзя: в задании нет такого сценария, по смыслу остаток приходит из складского учёта. Позиции с остатком 0 («Цезарь», «Апельсиновый фреш») поэтому навсегда остаются в стопе — так сразу видно заблокированную кнопку.
- **Истёкший срок.** Если время стопа уже прошло, при следующем чтении позиция автоматически возвращается в продажу.
- **Фильтр по статусу.** Если поставить позицию в стоп при фильтре «В продаже», строка не исчезает мгновенно, а остаётся с пометкой «сохраняется» и пропадает после обновления списка.
- **Пакетный менеджер.** Использовал pnpm вместо npm.

## Поведение на Vercel

Данные хранятся в памяти процесса. На serverless это значит, что:

- после деплоя, простоя или холодного старта всё возвращается к исходному сиду;
- если запросы попадут на разные инстансы, у них может быть разное состояние: например, после постановки в стоп обновлённый список придёт с инстанса, который об этом не знает, и позиция «вернётся».

Для тестового это ожидаемо. В реальном проекте данные хранились бы в базе.

## Что бы доделал или переделал

Переделал бы:

- **Время в бейдже.** Сейчас оно рендерится только на клиенте, поэтому при первой отрисовке на месте времени пусто. Правильнее знать часовой пояс заведения и форматировать время одинаково на сервере и клиенте.
- **Панель.** Фокус и закрытие по Esc сделаны вручную через `inert` и обработчик клавиш. Попробовал бы нативный `<dialog>`: он даёт это из коробки, но с ним сложнее анимировать закрытие.
- **Фильтры в URL.** Самописный хук на `pushState` хорош для двух фильтров. Если параметров станет больше, взял бы `nuqs` с типизированными парсерами.

Доделал бы:

- Хранение в базе или хотя бы в KV, чтобы состояние не терялось на serverless.
- Реальное время окончания смены из расписания заведения вместо абстрактного «до конца смены», а также работу в часовом поясе заведения, а не браузера.
- Синхронизацию остатков со складом или ручную корректировку остатка.
- Обновление списка в реальном времени (SSE или WebSocket), если с ним одновременно работают несколько менеджеров.
- E2E-тесты на Playwright для сценариев панели и фильтров.
- Включить React Compiler и убрать ручную мемоизацию.
